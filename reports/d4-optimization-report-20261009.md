# d4.cr 最適化の実装と再計測

2026-10-09。Crystal 1.21.1 `--release`、Rust d4binding / d4tools 0.3.11。以前の実装と改善後の実装を同じ D4 ファイルと公開 API で比較した。各条件は独立したプロセスで 4 回測定し、最初の 1 回を除く中央値。ページキャッシュが温まったローカルファイルのスポット計測であり、実データ 10 GiB の予測値ではない。

| 条件 | Crystal 改善前 | Crystal 改善後 | Rust C API | 改善後の最大 RSS |
|---|---:|---:|---:|---:|
| 一次データ 8M 塩基の書き込み | 5,132 ms | **807 ms²** | 87 ms | 3.4 MiB |
| 二次データ 1M 塩基の書き込み | 636 ms | **155 ms** | 24 ms | 3.5 MiB |
| 一次データ 64M 塩基の走査 | 547 ms | **167 ms** | 419 ms | 2.8 MiB |
| 一次データ 256M 塩基の走査 | 2,062 ms¹ | **683 ms** | 1,565 ms¹ | 2.8 MiB |
| 二次データ 20M 塩基の走査 | 654 ms | **259 ms** | 207 ms | 6.8 MiB |
| DEFLATE 二次データ 5M 塩基の走査 | 237 ms | **138 ms** | 591 ms | 3.4 MiB |
| 一次データ 4,096 点の参照 | 25.1 ms | **17.0 ms** | 3.7 ms | 2.8 MiB |

Crystal の書き込みは一次データで約 6.4 倍、二次データで約 4.1 倍速くなった。Rust C API と比べると、改善後もそれぞれ約 9.3 倍、約 6.5 倍の時間がかかる。一次走査は比較対象の Rust C API より速くなったが、前回の Rust CLI `stat -t 1`（約 134 ms）よりは遅い。CLI と C API は異なる処理経路であり、どちらか一方を「Rust 全体の速度」と解釈しない。

¹ 256M 塩基の改善前と Rust C API は先行計測の値。改善後は追加の 4 回測定で、最初を除く中央値を示した。先行計測の Rust CLI は約 573 ms。約 91.6 MiB のファイルで改善後の速度と小さい RSS が維持されたが、10 GiB の実測に代わるものではない。

² 一次データ書き込みに 8 値まとめて詰める追加改善を行った後の別の 4 回測定。追加改善前の同条件は 927 ms。幅 1・2・3・4・7・8 ビットのコード、辞書外値、チャンク境界をテストし、Rust CLI が出力の総和を確認した。

## 変更内容

- Writer は密な値を 20 バイト/塩基の run として保存せず、入力時に一次データを固定長バッファへビット詰めする。8 ビット以下の範囲辞書では 8 値をまとめて符号化する。辞書外値だけ二次記録をディスクへ退避する。既定値の長い区間は繰り返しパターンをバッファ単位で転写する。2.56 億塩基で最終点だけ書くケースは約 85 ms、最大 RSS 約 2.7 MiB で生成され、Rust CLI が合計値 7 を読み取った。
- 一次データの復号は塩基ごとのビット判定からビット蓄積方式に変更。二次レコードは通常フレーム内のコピーを省略。DEFLATE 展開バッファを再利用した。
- 二次ストリームが空の場合の点参照は直接一次データを読む。4,096 点の Crystal 累積 GC 割り当ては約 5.18 MiB から約 0.33 MiB に減った。圧縮 5M 塩基の走査では約 106 MB から約 56 MB に減った。
- Rust 0.3.11 の SUM 索引はデータ開始位置が 8 バイトなのに blob 長が 4 バイトヘッダーとして計算され、最後のビンが 4 バイト欠けるファイルがある。Crystal は完全なビンだけを索引から読み、不足する範囲は走査へ戻す。SFI のフィールド配置の違いを判定し、索引ディレクトリは子データ全体を含むサイズで記録する。

## 互換性と検証

- Rust 生成の索引付き 100K 塩基ファイルをテスト fixture として追加し、Crystal の SFI 点参照、SUM、境界の走査を確認した。
- Crystal が作成した索引付きファイルを Rust 0.3.11 の `d4tools index show SFI/SUM` と `d4tools stat -s sum -t 1` で確認した。索引なしの Crystal 作成一次・二次ファイルも Rust が読み取った。
- 35 件の Crystal spec（失敗 0 件）、Ameba、Crystal formatter を実行した。HTTP spec の 3 件は loopback socket が使える実行権限で実行した。

メモリ値は `wait4` の最大 RSS で、GC ヒープそのものではない。両実装の書き込み出力はサイズと配置が少し異なる。圧縮走査の累積 GC 割り当てはまだ約 56 MB ある。単発点参照は Rust C API より遅く、圧縮ストリームの細かいアクセス、大量の染色体や 10 GiB 級ファイル、ストレージキャッシュ外の読み出しは未測定である。

再現コードは `bench/compare.cr`、`bench/compare.c`、`bench/measure.c`。全サンプル値と中央値は `d4-optimization-measurements-20261009.json` に保存した。
